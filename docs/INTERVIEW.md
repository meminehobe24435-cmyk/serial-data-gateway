## 第 1 组：并发与队列

1. **为什么用"丢弃最旧"而不是"丢弃最新"或阻塞生产者？**
   → 采集是实时入口，阻塞会丢输入且不可恢复；丢最旧能保证最近的数据一定是全的，
   而现场排障最关心的就是"刚刚发生了什么"。丢弃数进 `STATS`，是可观测指标。

2. **`BoundedQueue::pop` 和 `popFor` 有什么区别？各自用在什么场景？**
   → `pop` 无限等待，用于"队列关不关"决定退出（分发线程）；
   `popFor(100ms)` 带超时，用于既要攒批、又要有周期 `fsync` 的消费者（落盘线程），
   避免用 `size()+sleep` 轮询白占 CPU 且丢精度。

3. **`condition_variable` 为什么必须配 `unique_lock`？为什么 `wait` 要带谓词？**
   → `wait` 需要解锁/加锁，所以必须 `unique_lock`；带谓词是为了防**虚假唤醒**，
   否则可能在队列仍为空时被唤醒继续往下走。

4. **`cv_.notify_all()` 和 `notify_one()` 在 `close()` 里为什么必须用 all？**
   → 关闭时要唤醒**所有**等待者，否则部分消费者会永久阻塞在 `wait` 上。

5. **如果要把这个队列改成无锁（lock-free）的，瓶颈在哪？**
   → 单生产者单消费者可以用环形缓冲 + 原子读写指针；但本项目有"满时丢最旧"的语义，
   MPSC 场景下需要 CAS 循环处理，复杂度上升，收益要看实测竞争程度 —— 没有数据就不要改。

## 第 2 组：网络与 epoll

6. **为什么所有 socket 都设非阻塞？`accept` 为什么要循环到 `EAGAIN`？**
   → 水平触发下就绪事件可能对应多个连接；`accept` 一次只取一个，
   不循环就会把剩余连接留到下次唤醒（延迟变大）。非阻塞保证循环不会卡死。

7. **水平触发（LT）和边缘触发（ET）的区别？这里用的哪个？**
   → 这里用默认的 **LT**：只要有数据没读完就还会通知，写起来不容易漏读。
   ET 只通知一次，必须一次读到 `EAGAIN`，且必须配合非阻塞，否则容易永久丢事件。

8. **TCP 粘包/拆包怎么处理的？**
   → 每个连接维护 `std::string in` 半包缓冲，`append` 收到的字节后循环查找 `'\n'`，
   切出完整命令行再处理，剩余部分留在缓冲里等下一批。

9. **`recv()` 返回 0 意味着什么？为什么不能立刻 `close()`？**
   → 返回 0 表示对端**半关闭**了写端（`shutdown(SHUT_WR)`），不是连接断了。
   此时已生成的响应还必须发出去。这就是 `read_closed` 标志存在的原因 —— 
   **开发时真的踩了这个坑**：`printf 'STATS\n' | nc` 什么都收不到。

10. **为什么要动态注册/取消 `EPOLLOUT`？一直注册会怎样？**
    → 一直注册会让 `epoll_wait` 在可写时不断唤醒（几乎总是可写），
    造成忙轮询白耗 CPU。所以只在有数据待写时注册，写空后立刻取消。

11. **慢消费者怎么保护？**
    → 每连接独立待写缓冲，超过 256 KB 直接断开该连接，不拖垮整个事件循环。

12. **`SIGPIPE` 为什么要忽略？**
    → 向已关闭的 socket 写会触发 `SIGPIPE`，默认行为是**直接杀进程**。
    忽略后 `send` 返回 `-1/EPIPE`，可以用错误码正常处理（这里还加了 `MSG_NOSIGNAL`）。

## 第 3 组：两个真实 bug（**重点，这两个是加分项**）

### Bug 1：TCP 半关闭导致响应丢失

- **现象**：`printf 'STATS\n' | nc 127.0.0.1 9000` 只能看到欢迎语，看不到 `STATS` 结果。
- **定位过程**：先用交互式 `nc`（不立刻 EOF）确认命令逻辑本身没问题 →
  说明问题出在"客户端提前 EOF"这条路径上 → 顺着 `recv()==0 → closeConn()` 读到根因。
- **根因**：把 `recv()==0` 当成"连接结束"，但那时响应还没写完。
- **修复**：拆成 `read_closed`（不再读）与 `out.empty()`（写完了）两个条件，
  两者同时满足才关连接；不再读时把关注事件从 `EPOLLIN` 改为只留 `EPOLLOUT`。
- **回归**：冒烟测试第 3 项就是这个用例。

### Bug 2：退出时丢最后一条数据

- **现象**：一致性测试报 `解析 148 帧 / 落盘 147 条`，差 1 条。
- **定位过程**：把三级流水线的计数都打出来对比（解析数 / 分发数 / 落盘数），
  发现差在"分发"这一步 → 说明记录进了队列但没被取走。
- **根因有两个**：① 分发线程写成 `while (!stop)`，信号一到就直接跳出，
  **没有排空队列**；② 主线程先 `close(store_q)` 再 join 分发线程，
  分发线程后续 `push` 的记录无人消费。
- **修复**：分发循环改成"排空到队列关闭为止"（`while (raw.pop(r))`）；
  主线程退出顺序改为 **停生产者 → join 采集 → 关 raw_q → join 分发 → 关 store_q → join 落盘**。
- **回归**：`tests/consistency_test.sh`，现在三级计数完全相等。

> 这两个 bug 值得在面试里主动讲 —— 它们证明你不是"抄了个能跑的 demo"，
> 而是真的把并发和网络细节走通了。

## 第 4 组：Linux 系统编程细节

13. **串口 raw 模式为什么用 `cfmakeraw`？`VMIN`/`VTIME` 是什么？**
    → `cfmakeraw` 关掉回显、行缓冲、信号生成等"终端语义"，得到纯字节流；
    `VMIN=0` + `VTIME=0` 配合 `O_NONBLOCK` 就是完全不阻塞的读，方便和 `poll` 配合。

14. **`O_NOCTTY` 为什么重要？**
    → 防止打开串口时它变成进程的控制终端，否则串口上的信号可能影响本进程。

15. **self-pipe trick 解决什么问题？**
    → 信号处理器里只能调异步信号安全函数。用管道把"信号到达"这个事件
    转成"管道可读"，让主线程用正常逻辑处理收尾（`join`、`close` 都不安全）。

16. **`fsync` 和 `fdatasync` 的区别？为什么每秒一次而不是每批一次？**
    → `fdatasync` 只刷数据不刷元数据，通常更快；`fsync` 更保守。
    每次写都 `fsync` 会让吞吐暴跌，每秒一次把掉电丢失窗口控制在秒级，是折中。

17. **`write` 会不会少写？**
    → 会。对普通文件一般不会，但对管道/socket 必须循环写。
    本项目落盘用普通文件 + 单线程顺序写，所以没做循环写 —— 
    **但这一点要能说清楚，面试官可能会追问。**
